明白了，这个信息很关键——它改变了我的裁决前提：目的不是「给 Horosa 上基础设施」，而是**借这个项目把全流程走一遍**。那么裁决标准就不是「要不要学」，而是「每个学习环节有没有真实的验证场景」。**工具不匹配项目形态 = 假动作，做完了也学不到东西，面试时还立不住。**

## 核心原则：全流程 ≠ 全家桶

全流程是：需求 → 设计 → 编码 → 测试 → 构建 → 集成 → 发布 → 运维。**每个环节都真实发生**才是全流程；装一堆组件但没有对应的真实场景，那是流程表演。

关键认知：这个项目的「发布」环节的真实形态不是部署到服务器，而是**桌面安装包 + GitHub Release**。这才是它的 CD。

## 企业流程环节 → Horosa 里的真实对应物

| 企业模板里的环节 | Horosa 的真实对应 | 状态 |
|---|---|---|
| CI（构建+测试） | GitHub Actions：`mvn verify` + golden diff + vitest + pytest | ✅ 做，双机等价性真有用 |
| 代码质量 | **SonarCloud**（GitHub 免费集成，不用自建服务端） | ✅ 做，替代自建 SonarQube |
| 镜像仓库 Harbor | **GitHub Releases**（发布的就是安装包/构建产物） | ✅ 用 Releases 替代 |
| CD 自动部署 | **Tauri 打包 → 签名 → GitHub Release**，带版本号和 changelog | ✅ 这是桌面应用的真实 CD，远期做 |
| 容器化 | **限定用途**：Docker Compose 只用来固定 golden test 的 MySQL 环境（录制/回放同库，消灭「我机器上能跑」） | ✅ 有限做 |
| 监控 | Actuator health 端点 + 结构化日志 | ✅ 轻量做 |
| Jenkins / ELK / SkyWalking / K8s / Helm | 无验证场景 | ❌ 删，硬学是空转 |
| JMeter 压测 | 对 `:9999` 排盘接口做并发基线有一点演示价值 | ⏸ 可选，排最后 |

这样调整后，你的全流程闭环是：**需求文档 → 设计 → 编码 → 测试基线 → CI 门禁 → SonarCloud 质量门 → 打包 → GitHub Release 发布 → 复盘记录**——八环全真，每一环都能在面试里讲出数字。比七个阶段的全家桶更完整，因为它没有一环是演的。

## 贯穿全程的五条纪律

1. **双机**：离开必 commit+push（wip 也行，禁 stash），到达必 `pull --ff-only`，依赖只 `npm ci` / `mvn` 标准命令
2. **一次一个变量**：Boot 与 JDK 分两步，每步独立提交，实验日志记录每个报错与解法
3. **没有基线不动代码**：盘点的四张清单先出，golden 先录，再谈升级
4. **周日仓库卫生检查**：两台 `git status` 干净、CI 绿、`.nvmrc` 与实际一致——十分钟
5. **禁止项常驻脑中**：事故注释模块不重写、`javax` JDK 系四包禁改、全局替换禁用、Tauri 四约束 + Safari 15 语法禁令
