是的。如果你的目标不只是把 Horosa 改造完成，而是借这个项目完整走一遍现代 Java 企业级软件的开发、测试、部署、运维和性能优化流程，那么 CI/CD、Docker、Jenkins、日志监控、JVM 调优等都应该纳入计划。

但我建议你不要一开始就把所有工具全部装好。

更合理的做法是：从项目第一天开始建立工程规范和自动化基础设施，然后随着项目开发逐步启用测试、持续集成、部署、监控和性能工程。

你最终需要掌握的不只是 Spring Boot，而是一整套软件工程能力。

### 5. CI/CD 持续集成与持续交付

项目初期建立基础，逐步完善

这是你提到的 Jenkins 所在的领域。

先理解两个概念：

- CI（Continuous Integration）：代码提交后，自动编译、测试、检查。
- CD（Continuous Delivery/Deployment）：自动生成发布制品，并将应用部署到测试或生产环境。

推荐技术：

| 技术               | 用途              |
| ---------------- | --------------- |
| Jenkins          | 自动化构建、测试和部署     |
| Jenkins Pipeline | 用代码定义流水线        |
| Jenkinsfile      | 保存流水线配置         |
| GitHub Actions   | GitHub 内置 CI/CD |
| GitLab CI/CD     | GitLab 内置 CI/CD |

我建议你实际使用 Jenkins。

因为你的目标是完整体验企业级 DevOps 流程，而不仅仅是让代码自动编译。

可以设计这样的流水线：

Horosa CI/CD Pipeline

1. Git Push：开发者提交代码
2. Checkout：Jenkins 获取代码
3. Build：Maven / pnpm / uv 构建
4. Test：自动化测试
5. Quality：SonarQube 代码质量分析
6. Security：依赖和镜像安全扫描
7. Package：生成 JAR 和前端构建产物
8. Docker Build：生成 Docker 镜像
9. Registry：推送镜像仓库
10. Deploy：部署到测试环境
11. Verify：健康检查和部署验证

生产环境发布则增加人工审批、备份和回滚机制。

Jenkins 可以通过 Jenkinsfile 管理流水线，也支持使用 Docker 容器作为构建环境。

### 8. JVM 性能分析与调优

必须学习，实际性能测试后再调优

这是你特别提到的部分，也是 Java 后端工程师的重要能力。

需要掌握的工具：

| 工具                       | 作用                 |
| ------------------------ | ------------------ |
| JDK Flight Recorder（JFR） | 记录 JVM 运行行为        |
| JDK Mission Control（JMC） | 分析 JFR 数据          |
| VisualVM                 | 查看 JVM 运行状态        |
| jcmd                     | 查询 JVM 诊断信息        |
| jstack                   | 查看线程堆栈             |
| jmap                     | 分析堆内存、生成 Heap Dump |
| async-profiler           | CPU、内存及锁竞争分析       |
| JMH                      | Java 微基准测试         |

重点学习以下内容：

| 知识领域   | 具体内容            |
| ------ | --------------- |
| JVM 内存 | 堆、栈、元空间、直接内存    |
| 垃圾回收   | G1 GC、ZGC、GC 日志 |
| 线程     | 线程池、锁、死锁、并发     |
| 类加载    | 类加载器、双亲委派       |
| 内存问题   | 内存泄漏、OOM、频繁 GC  |
| 性能诊断   | CPU 飙高、响应慢、线程阻塞 |

建议实际完成三个实验：

1. 人为制造内存泄漏，使用 JFR、Heap Dump 定位问题。
2. 制造线程阻塞和死锁，使用线程堆栈分析。
3. 制造高并发请求，对比不同 JVM 参数下的吞吐量、延迟和 GC 情况。

不要一开始就把 JVM 参数调得很复杂。

先使用合理默认配置，建立性能基线，再根据实际测试结果调整 G1、ZGC、堆内存和线程池。

### 9. 性能测试与系统可靠性

功能基本完成后进行

| 技术           | 用途            |
| ------------ | ------------- |
| JMeter       | 接口压力测试        |
| k6           | HTTP/API 性能测试 |
| Gatling      | 高并发性能测试       |
| JMH          | Java 代码微基准测试  |
| Resilience4j | 熔断、限流、重试等     |
| HikariCP     | 数据库连接池        |
| Redis        | 缓存            |
| Caffeine     | Java 本地缓存     |

建议围绕 Horosa 做一些真实的性能实验：

- 100、500、1000 个并发用户访问登录接口。
- 大量用户同时查询星盘或排盘结果。
- 每日一练 FastAPI 服务同时处理多个 AI 请求。
- 模拟 Redis 故障、数据库连接中断。
- 模拟 Python 服务响应超时。
- 观察 Java 服务是否出现线程池耗尽。

你需要掌握的不只是 TPS，还包括：

- 平均响应时间。
- P95、P99 响应时间。
- 错误率。
- CPU、内存使用率。
- GC 停顿时间。
- 数据库连接池等待时间。

这些指标才能说明系统是否真正稳定。

## 六、几个我特别希望你注意的地方

第一，不要把 CI/CD 理解为 Jenkins 安装。

Jenkins 只是执行自动化流程的工具。真正需要你掌握的是：

- 如何构建流水线。
- 如何执行测试。
- 如何管理环境变量和密钥。
- 如何构建 Docker 镜像。
- 如何部署和回滚。
- 如何处理构建失败和部署失败。

第二，不要把 JVM 调优放在项目初期。

先完成业务功能和监控，再建立性能基线，最后通过压力测试定位瓶颈。没有数据就调 JVM 参数，通常是在盲目优化。

第三，不要一开始就使用 Kubernetes。

你之前也提到过 Docker 和 Linux 基础已经有一些，但 Kubernetes 还不熟悉。建议先用一台 Linux 服务器把 Docker Compose、Nginx、Jenkins 和监控体系跑通，再考虑多节点 K8s。

第四，Java、React、Python 应该分别建立流水线。

它们可以由同一个 Jenkins 管理，但各自独立构建、测试和发布，避免一个服务修改就必须重新部署整个系统。
